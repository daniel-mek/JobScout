# Phase 5: applications

Application tracking runs beside the legacy tracker; no private history is imported or modified. Open a job and choose **Prepare Application**, then complete the external submission yourself. **Mark as Applied** requires an explicit submission confirmation and an owned, confirmed resume version. It records the first submission timestamp and resume used. Later stages require a recorded submission. Reopening an existing posting retains the same application and history rather than creating a duplicate, including terminal applications.

`/applications` provides a responsive Kanban and table/list view, company/role/status filters, database pagination and CSV export. Cards can be dragged between statuses or moved with a labelled keyboard-accessible select. Moving an unsubmitted application to Applied opens its detail page for confirmation and resume selection. All status changes persist previous/new status, precise timestamp, USER source and optional note. Optimistic revisions reject stale status/next-action writes; owner advisory locks serialize PostgreSQL mutations.

`/applications/[id]` shows the timeline, resume download, archived job and match evidence, chronological notes, dated assessment/interview/application/follow-up events, reversible completion, and next-action text/date. The next due date includes incomplete dated events and the explicit next-action date. Dates are calendar dates; timestamps display UTC. For an Applied application, a configurable 1–90 days of recorded inactivity yields an on-demand **Consider following up** suggestion. Recording activity resets it. This does not contact anyone, schedule delivery, or imply unrecorded employer activity was checked. Durable reminders remain Phase 7.

Snapshots are captured once at Saved (when created explicitly through the API), Preparing and first Applied. The submitted snapshot takes precedence for tracker display. Posting revisions, inactivity and later source changes never overwrite the captured listing or match. A submitted snapshot only records a cached match for the selected resume and current job revision; no match is invented when missing. Match timestamp/profile/resume/algorithm metadata are retained. Each snapshot keeps source attribution and original links. Source storage policies apply at capture and at read time; tightening restrictions purges descriptions and derived matches from these archives too. This documented retention exception takes precedence over archive immutability.

The API separates application models, validated inputs, routes and business services. All records are owner-scoped and mutations use the existing session/Origin/CSRF protections. A unique owner/posting constraint prevents duplicates. CSV contains tracking fields, recorded scores, resume version number, chronological notes, attribution and source URLs without internal identifiers or archived descriptions. Formula-prefixed values are escaped for spreadsheets. The bounded export supports up to 10,000 applications and rejects larger exports explicitly.
